Hazard Analysis and Industry Standard Mapping

Although this project is an educational demonstration rather than a flight-certified system, it models a common real-time systems problem: priority inversion. The following analysis identifies potential hazards resulting from improper synchronization and discusses how priority inheritance mitigates those hazards.

This analysis is intended to demonstrate engineering methodology rather than certify compliance with any aerospace or safety standard.

Hazard Identification

Hazard Cause Potential Effect Mitigation
Priority inversion Low-priority task owns a shared resource while a medium-priority task preempts it. Flight Control experiences excessive blocking, delaying control outputs. Use a mutex supporting priority inheritance.
Missed control deadlines Flight Control waits excessively for the navigation resource. Delayed attitude corrections and degraded vehicle stability. Bound blocking time through priority inheritance and minimize critical sections.
CPU starvation Computationally intensive Terrain Mapping monopolizes processor time. Increased response time for lower-priority tasks. Assign appropriate priorities and reduce execution time where possible.
Shared resource contention Multiple tasks require exclusive access to navigation data. Blocking and increased response time. Keep critical sections short and use ownership-aware synchronization primitives.

Risk Assessment

Hazard Likelihood Severity Overall Risk
Priority inversion Possible High High
Missed control deadline Possible High High
CPU starvation Likely Medium Medium
Resource contention Certain Medium Medium

Mitigation Strategy

The primary mitigation demonstrated by this project is replacing a binary semaphore with a FreeRTOS mutex implementing priority inheritance.

When the Flight Control task blocks while waiting for a mutex held by the Telemetry Logger, FreeRTOS temporarily raises the logger's priority to match the waiting task. This prevents the Terrain Mapping task from preempting the logger and bounds the Flight Control task's blocking time.

The measured response times presented on the timing analysis page demonstrate the effectiveness of this mechanism.

Industry Standard Mapping

Standard Relationship to this Project
DO-178C Emphasizes deterministic software behavior, timing verification, and requirements-based verification. This project demonstrates deterministic synchronization and timing analysis concepts.
MISRA C Encourages predictable, maintainable embedded software. The project follows a structured task organization and avoids dynamic synchronization behavior during runtime.
NASA Software Engineering Handbook Recommends bounded execution time, deterministic task behavior, and careful resource sharing in safety-critical software. Priority inheritance directly supports these objectives.
FreeRTOS Design Guidelines Recommend mutexes rather than binary semaphores when ownership and priority inheritance are required.

Lessons Learned

  • Priority inversion is fundamentally a resource-sharing problem, not simply a scheduling problem.
  • Priority inheritance bounds blocking time without changing application behavior.
  • Worst-case response time depends on both computation and resource contention.
  • Selecting the correct synchronization primitive is critical for deterministic real-time performance.

Conclusion

This project demonstrates that replacing a mutex with a binary semaphore can dramatically increase the response time of a high-priority task, despite no changes to application logic. The results reinforce a fundamental principle of real-time software engineering: deterministic synchronization is essential for maintaining predictable timing behavior in safety-critical systems.
