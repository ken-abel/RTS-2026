System Architecture

This project implements a simplified aerospace flight control system running on an ESP32 using FreeRTOS. The purpose of the system is to demonstrate how improper resource locking can create priority inversion in a real-time embedded system.

Three concurrent tasks operate with different priorities. The Flight Control task requires access to a shared navigation resource that is periodically locked by the lower-priority Telemetry Logger task. The Terrain Mapping task creates CPU interference and demonstrates how priority inversion can increase worst-case execution time (WCET).

Design Decisions

This project was intentionally designed to isolate the effects of priority inversion while remaining simple enough to analyze. Several implementation decisions were made to emphasize deterministic behavior and clearly demonstrate the differences between synchronization mechanisms.

Design Decision Rationale
ESP32 running FreeRTOS Provides a realistic embedded platform with a widely used real-time operating system supporting priority-based preemptive scheduling.
FreeRTOS Mutex Demonstrates priority inheritance, allowing a low-priority task holding a shared resource to temporarily inherit the priority of a blocked high-priority task.
Binary Semaphore Used as a comparison because binary semaphores do not track ownership and therefore cannot implement priority inheritance.
Three-task priority hierarchy Models the classic priority inversion scenario using one high-priority task, one medium-priority task, and one low-priority task sharing a resource.
CPU-bound critical section The Telemetry Logger performs computational work while holding the shared resource so that blocking time is measurable and affected by task scheduling.
User-triggered Terrain Mapping The medium-priority task only executes when the pushbutton is pressed, allowing the effects of priority inversion to be demonstrated on demand.
LED status indicator The onboard LED remains illuminated while the Flight Control task is blocked, providing an immediate visual indication of response-time differences.
Serial timing measurements Execution timestamps from esp_timer_get_time() provide microsecond-resolution measurements for WCET and response-time analysis.
Slowed Flight Control period (1 second) The actual control period was increased from 10 ms to 1 s to make task interactions and priority inversion easier to observe during demonstration.
Martian drone scenario Provides an aerospace-inspired application where deterministic task execution and bounded response times are safety-critical.

Data Flow

The Flight Control and Telemetry Logger tasks both require access to a shared navigation data structure protected by a synchronization object. The Flight Control task periodically requests this resource to compute attitude corrections, while the Telemetry Logger accesses it to upload position data to the host spacecraft.

The Terrain Mapping task performs image and lidar processing without using the shared resource. This makes it an ideal source of interference for demonstrating priority inversion, since it competes only for CPU time and not for the protected data itself.

Two external events initiate system activity:

  • A periodic timer releases the Flight Control task once every second.
  • A GPIO interrupt generated by the pushbutton signals the Terrain Mapping task through a binary semaphore.

Switching between a FreeRTOS mutex and a binary semaphore is controlled by the USE_PI_MUTEX compile-time flag. This allows the same application code and workload to be evaluated with and without priority inheritance, isolating the effects of the synchronization primitive on system response time.

Implementation Notes

The application logic is identical in both experimental configurations. The only change between trials is the synchronization primitive used to protect the shared navigation resource. This ensures that any observed difference in Flight Control response time results solely from the presence or absence of priority inheritance.

Task Responsibilities

Task Priority Purpose
Control Loop Task 20 Periodically releases the Flight Control task every control cycle.
Flight Control 15 (High) Performs attitude and trajectory corrections. Requires access to the shared navigation resource.
Terrain Mapping 10 (Medium) Processes simulated camera and lidar data. Does not access the shared resource, but consumes CPU time.
Telemetry Logger 5 (Low) Uploads navigation data to the spacecraft. Holds the navigation lock during its critical section.

Synchronization Design

The primary synchronization challenge in this system is protecting the shared navigation resource. Both the Flight Control and Telemetry Logger tasks require access to this resource.

Configuration Behavior
USE_PI_MUTEX = 1
FreeRTOS Mutex 		Priority inheritance is enabled. When the Flight Control task blocks waiting for the Telemetry Logger, the logger temporarily inherits the higher priority and completes its critical section without being interrupted by Terrain Mapping.
USE_PI_MUTEX = 0
Binary Semaphore 		No ownership or priority inheritance exists. Terrain Mapping can preempt the Telemetry Logger while the Flight Control task waits, increasing the blocking time.

Priority Inversion Flow

The failure scenario occurs as follows:

  1. Telemetry Logger (low priority) acquires the navigation lock.
  2. Flight Control (high priority) becomes ready and requests the same lock.
  3. Flight Control blocks while waiting for the resource.
  4. Terrain Mapping (medium priority) begins executing and preempts the Telemetry Logger.
  5. Flight Control cannot proceed until both Terrain Mapping and Telemetry Logger complete.

With priority inheritance enabled, the Telemetry Logger temporarily executes at the Flight Control priority, preventing Terrain Mapping from extending the blocking duration.

Implementation Notes

  • Platform: ESP32 running FreeRTOS
  • Scheduler: Preemptive real-time scheduler
  • Shared resource: Navigation data lock
  • Demonstration modes: USE_PI_MUTEX = 1 (mutex) and USE_PI_MUTEX = 0 (binary semaphore)
