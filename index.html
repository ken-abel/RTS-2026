Project Overview

A simulated and simplified flight control system that correctly handles priority inversion, built to demonstrate the importance of proper mutex implementation in an aerospace embedded system.

The Scenario

A small drone, deployed from a nearby spacecraft currently orbiting Mars, needs to adjust its attitude and trajectory, map the surface, and routinely log its flight path to a database located on the larger spacecraft.

Using three tasks with the priority hierarchy in the task table, this project demonstrates the importance of resource lock ownership and its impact on worst-case execution time (WCET) for tasks sharing a resource.

Task Table

Task Priority Function
Flight Control High Computes engine thrust and attitude corrections every 10 ms.
Note: This period has been slowed to 1 second for the purpose of demonstrating priority inversion.
Terrain Mapping Medium Processes camera and lidar data to avoid hazards.
Telemetry Logger Low Uploads flight data to the nearby host ship.

Priority Inversion Scenario

The Telemetry Logger locks the navigation mutex to upload current positional data to the nearby spacecraft.

The Flight Control task periodically becomes ready each control cycle, requiring access to the navigation mutex.

The Terrain Mapping task processes lidar and camera frames upon manual request from the nearby spacecraft (simulated by pressing a button). This task is computationally intensive and resource-heavy.

Priority Inheritance

The Flight Control task must quickly respond to disturbances or detected obstacles and hazards. Due to the presence of the mutex and the given priority hierarchy, priority inversion is possible.

To prevent this, priority inheritance must be enabled so that the Terrain Mapping task cannot preempt the Telemetry Logger while the Flight Control task is waiting for the navigation mutex.

To simulate priority inheritance being disabled, a binary semaphore can be used in place of a mutex by setting: 

USE_PI_MUTEX = 0
