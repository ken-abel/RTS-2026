Project Overview

A simulated and simplified flight control system that demonstrates priority inversion and the importance of proper mutex implementation in an aerospace embedded system.

The Scenario

A small drone, deployed from a nearby spacecraft currently orbiting Mars, needs to adjust its attitude and trajectory, map the surface, and routinely log its flight path to a database located on the larger spacecraft.

Using three tasks with different priority levels, this project demonstrates the importance of resource lock ownership and its impact on worst-case execution time (WCET) for tasks sharing a resource.

Task Table

Task Priority Function
Flight Control High (15) Computes engine thrust and attitude corrections every 10 ms.

Note: This period has been slowed to 1 second for the purpose of demonstrating priority inversion.
Terrain Mapping Medium (10) Processes camera and lidar data to avoid hazards. This task is intentionally CPU-intensive to demonstrate interference.
Telemetry Logger Low (5) Uploads flight data to the nearby host spacecraft and accesses the shared navigation resource.

Priority Inversion Scenario

The Telemetry Logger locks the navigation mutex to upload current positional data to the nearby spacecraft.

The Flight Control task periodically becomes ready during each control cycle and requires access to the navigation mutex.

The Terrain Mapping task processes lidar and camera frames upon manual request from the nearby spacecraft (simulated by pressing a button). This task is computationally intensive and consumes significant CPU time.

Priority Inheritance

The Flight Control task must quickly respond to disturbances or detected obstacles and hazards. Due to the priority hierarchy and shared mutex, priority inversion is possible.

With priority inheritance enabled, the Telemetry Logger temporarily inherits the Flight Control task's priority while holding the mutex. This prevents Terrain Mapping from preempting the logger and extending Flight Control's blocking time.

To simulate priority inheritance being disabled, a binary semaphore can be used instead of a mutex by setting: 

USE_PI_MUTEX = 0

WCET and Priority Inversion Timing Analysis

WCET measurements were collected for each task during execution. Additionally, lock acquisition latency was measured for the Flight Control task to quantify the effect of priority inversion. The lock acquisition delay is reported separately from task WCET because it represents scheduling interference and resource blocking rather than computation time.

Task Period WCET Response time With Prio. Inheritance (Mutex) Response time Without Prio. Inheritance (Bin Sem)
Flight Control 1000 ms 24.65 ms 252 ms ~1,000-2,250 ms
Terrain Mapping User-determined 2,953.7 ms - -
Telemetry Logger ~550 ms 421.0 ms - -

Note that the response time of the Flight Control task is that of the WCET of the Terrain Mapper when priority inheritance is disabled.

Without the terrain mapper, the CPU Utilization is 0.8. This is below the Rate-Monotonic sufficiency bound for a two-task system, meaning that using Rate Monotonic (and Earliest Deadline First) scheduling will result in a schedulable set of tasks. However, adding the terrain mapper will immediately cause the system to lose both RM and EDF-scheduling feasibility- this is intentional. This exaggerates the response time of the Flight Control task so that priority inversion can be easily seen, either by watching the LED or reading the log.

With Priority Inheritance enabled, you can see an interesting effect of the Terrain Mapper starving the Telemetry Logging task-- if you repeatedly press the button, initiating the terrain mapping task, the Flight Control task's delay drops to just two milliseconds consistently. This is because the Terrain Mapper is starving the CPU and preventing the Telemetry Logger from unblocking, despite being ready, thus opening the window for the Flight Controller to take the mutex and immediately preempt the Terrain Mapper.

It is also interesting that the maximum response time of the Flight Controller with priority inheritance enabled was slightly more than half of the WCET for the Telemetry Logger, over more than 100 trials. I expected it to approach 421.0 ms. This may reflect my WCET-measurement technique requiring logging and CPU tick polling functions adding some execution time to the task, but it should be minimal, and not on the order of 200 milliseconds. This may be worth investigating going forward.
