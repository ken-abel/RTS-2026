Task Table, WCET, and Response Time Analysis

This page summarizes the timing characteristics of the simulated flight control system and compares system behavior when using a FreeRTOS mutex (priority inheritance enabled) versus a binary semaphore (priority inheritance disabled).

Task Table

Task Priority Period Purpose
Flight Control 15 (High) 1000 ms* Computes engine thrust and attitude corrections. The control period has been intentionally slowed from 10 ms to 1 s so priority inversion can be easily observed.
Terrain Mapping 10 (Medium) User-triggered Processes camera and lidar data. CPU-intensive and does not access the shared resource.
Telemetry Logger 5 (Low) ~550 ms Uploads flight data while holding the shared navigation lock.

Worst-Case Execution Time (WCET)

Worst-case execution times were measured for each task individually. Response time for the Flight Control task is reported separately because it includes mutex blocking time caused by contention for the shared navigation resource.

Task Period Observed WCET
Flight Control 1000 ms 24.65 ms
Terrain Mapping User Triggered 2953.7 ms
Telemetry Logger ~550 ms 421.0 ms

Flight Control Response Time

Unlike WCET, response time includes both execution time and any blocking caused by synchronization. The values below measure the elapsed time between the Flight Control task requesting the shared navigation resource and successfully acquiring it.

Synchronization Method Observed Response Time
FreeRTOS Mutex (Priority Inheritance Enabled) 252 ms
Binary Semaphore (No Priority Inheritance) ~1000 – 2250 ms

Notice that the maximum response time without priority inheritance approaches the execution time of the Terrain Mapping task, demonstrating that the medium-priority task is extending the blocking time experienced by the Flight Control task.

CPU Utilization and Schedulability

Without the Terrain Mapping task executing, total CPU utilization is approximately 0.80. This remains below the Rate-Monotonic sufficiency bound for a two-task system, so the Flight Control and Telemetry Logger tasks are schedulable.

Activating the Terrain Mapping task intentionally increases processor utilization beyond both the Rate-Monotonic and Earliest Deadline First schedulability limits. This exaggerates the effects of priority inversion, making the difference between a mutex and a binary semaphore easy to observe in both the serial log and the on-board LED.

Experimental Observations

An interesting behavior was observed while repeatedly triggering the Terrain Mapping task with priority inheritance enabled. Despite the Terrain Mapping task consuming nearly all available processor time, the Flight Control task often acquired the mutex after waiting only about two milliseconds.

This occurs because the Terrain Mapping task prevents the Telemetry Logger from beginning another critical section. When the Flight Control task becomes ready, it is frequently able to acquire the mutex immediately before the Telemetry Logger resumes execution.

Discussion

The maximum observed response time with priority inheritance enabled was approximately 252 ms, slightly more than half of the measured WCET of the Telemetry Logger's critical section. Intuitively, a value closer to 421 ms was expected.

One possible explanation is that the instrumentation used to measure execution time (serial logging and timestamp polling) slightly affects task execution. Another possibility is that the asynchronous timing of task releases rarely allows the Flight Control task to encounter the Telemetry Logger immediately after it acquires the mutex. Further investigation would be required to determine the precise cause.
